# Hypothesis 1 - Technical Plan

## מטרת התוכנית
המטרה הטכנית של טענה 1 היא לבנות תהליך שמאפשר לבדוק, באופן אמפירי ושחזורי, האם מחלקות הקרקוע מכסות את שאלות ה-QA/RAG בדאטסטים מבוססי מסמכים. התהליך צריך להתחיל מאיתור דאטסטים, כי יש סיכון ממשי שהדאטסטים הפומביים אינם מכילים מספיק שאלות מהסוגים שמעניינים את המחקר: שאלות על ישויות ארגוניות ואגרגציה עליהן.

לכן סדר העבודה אינו "מגדירים טקסונומיה ואז מריצים על כל מה שמוצאים", אלא:

1. בודקים שיש דאטסטים שמאפשרים ניסוי משמעותי.
2. מייצרים פרוטוקול תיוג שמבוסס על תוכנית פעולה אנושית.
3. בונים מנגנון תיוג סוכני שמייצר trace שניתן לבקר.
4. מאמתים אנושית את התיוג.
5. מחשבים כיסוי ושארית.

## שלב 0 - שער ישימות דאטסטים
לפני פיתוח מלא של pipeline, צריך לבצע סקר דאטסטים ולייצר registry ראשוני. השלב הזה יגובש בהמשך כמסמך רשמי נפרד על בסיס בדיקות הדאטסטים. הסקירות שנמצאות תחת `hypotheses/datasets/deep_research` הן חומרי גלם לא מחייבים שמטרתם להרחיב את המבט, ולא החלטת תכנון סופית.

תוצרי השלב:

```text
datasets/candidates.csv
reports/dataset_discovery.md
reports/feasibility_gate.md
```

החלטת מעבר:

1. מעבר מלא אם נמצאו 6-8 דאטסטים רלוונטיים, ומתוכם 1-2 עם פוטנציאל ממשי ל-30-40 אחוז שאלות אונטולוגיה ואגרגציה יחד.
2. מעבר חלקי אם נמצאו דאטסטים טובים אך ללא ייצוג מספיק למחלקות הארגוניות; במקרה כזה צריך לעדכן את נוסח הטענות לפני המשך.
3. עצירה מתודולוגית אם אין מספיק דאטסטים שמאפשרים תיוג אמין; במקרה כזה המאמר עשוי להפוך לטענת gap על בנצ'מארקים.

## שלב 1 - קיבוע גרסה ראשונית של הטקסונומיה
צריך לייצר גרסה ראשונה של schema והנחיות תיוג. ההנחיות לא צריכות להיות מושלמות, אבל הן צריכות להיות מספיק חדות כדי להריץ פיילוט.

התוצרים:

```text
label_schema.json
annotation_guidelines.md
examples/boundary_cases.md
```

ה-schema צריך לכלול:

1. ארבע מחלקות הקרקוע המרכזיות.
2. תוויות עזר.
3. אפשרות לתוויות מרובות.
4. תיוג ברמת צעד וברמת שאלה.
5. confidence ו-uncertainty.
6. סיבת הכרעה קצרה לכל תווית.

## שלב 2 - נרמול הדאטה
צריך לבנות pipeline שממיר כל דאטסט לפורמט רשומות אחיד. בשלב הראשון אפשר לכתוב ממירים נקודתיים לכל דאטסט, אבל הפורמט הסופי צריך להיות אחיד.

פורמט מומלץ:

```json
{
  "benchmark_id": "...",
  "question_id": "...",
  "question": "...",
  "answer": "...",
  "evidence": [],
  "source_documents": [],
  "document_metadata": {},
  "benchmark_annotations": {},
  "available_context_level": "...",
  "known_limitations": []
}
```

שדות חשובים במיוחד:

1. `evidence`: ראיות שסופקו על ידי הדאטסט, אם קיימות.
2. `source_documents`: מסמכי המקור או מזהים שלהם.
3. `document_metadata`: תאריך, מקור, גרסה, היררכיה, סוג מסמך, ישות מקושרת אם קיימת.
4. `known_limitations`: למשל "אין גישה למסמכי מקור", "רק evidence spans", או "אין מטאדאטה".

## שלב 3 - פיילוט תיוג ידני
לפני תיוג סוכני רחב, צריך לבצע פיילוט ידני קטן שמטרתו לחדד את ההנחיות ולזהות מוקדי בלבול.

מדגם מוצע:

1. 30-50 שאלות מדאטסט ראייתי יחסית.
2. 30-50 שאלות מדאטסט עם אופי ארגוני או תמיכתי.
3. 30-50 שאלות מדאטסט עם טבלאות, ערכים או חישובים.

לכל שאלה המתייג יכתוב:

```json
{
  "action_plan": [
    {
      "step": "מה אדם היה עושה",
      "needed_source": "איזה מקור קרקוע צריך להשיג",
      "step_labels": ["metadata"],
      "evidence_for_label": "למה זה הצעד"
    }
  ],
  "question_labels": ["metadata", "textual_evidence"],
  "auxiliary_labels": [],
  "confidence": 0.0,
  "uncertainty": ""
}
```

הדגש הוא לא לבקש מהמתייג לבחור תווית מיד, אלא להכריח אותו לנסח את דרך הפתרון. התוויות צריכות לנבוע מהצעדים.

## שלב 4 - סוכן תיוג מבוסס תוכנית פעולה
הכיוון המרכזי הוא לפתח מנגנון תיוג סוכני. המנגנון יקבל שאלה, תשובה והקשר זמין, וינסה לשחזר מה אדם היה צריך לעשות כדי להגיע לתשובה. הוא לא יסתפק בבחירת label, אלא יפיק trace שמאפשר ביקורת.

### קלט הסוכן
הסוכן יקבל את השדות הבאים, בהתאם לזמינות בכל דאטסט:

1. נוסח השאלה.
2. תשובת gold.
3. ראיות שסופקו.
4. מסמכי מקור או קטעים רלוונטיים.
5. מטאדאטה ומבנה, אם קיימים.
6. annotations קיימים, למשל supporting facts, source document, answer type או program.

### פעולות מותרות לסוכן
בשלב המחקרי, הסוכן יכול לבצע כמה צעדי ניתוח שהוא צריך:

1. לקרוא את השאלה והתשובה.
2. לבדוק את הראיות שסופקו.
3. לחפש במסמכי המקור, אם הם זמינים.
4. לבדוק מטאדאטה או היררכיה, אם קיימות.
5. לזהות ישויות חוזרות ומופעים שלהן.
6. לבדוק האם נדרש איסוף רחב, קיבוץ או חישוב.
7. לנסח תוכנית פעולה אנושית.
8. לתייג כל צעד לפי מחלקת קרקוע.

### פלט הסוכן
הפלט צריך להיות JSON תקין ושחזורי:

```json
{
  "action_plan": [
    {
      "step_id": 1,
      "human_action": "",
      "grounding_source_needed": "",
      "step_labels": [],
      "supporting_dataset_fields": [],
      "confidence": 0.0,
      "notes": ""
    }
  ],
  "question_labels": [],
  "auxiliary_labels": [],
  "coverage_status": "covered | insufficient_context | out_of_scope",
  "rationale": "",
  "uncertainty": "",
  "possible_dataset_bias": ""
}
```

הסוכן צריך להישפט לפי איכות תוכנית הפעולה והיכולת לבקר את התוויות, לא רק לפי התאמת label סופית.

## שלב 5 - השוואה בין תיוג אנושי לסוכן
לאחר פיילוט הסוכן, צריך להשוות אותו לתיוג האנושי:

1. התאמה ברמת שאלה: האם קבוצת התוויות הסופית דומה.
2. התאמה ברמת צעד: האם הסוכן זיהה את אותם סוגי פעולות.
3. זיהוי שגיאות אופייניות: נטייה למשוך שאלות לראיות, פספוס מטאדאטה, פספוס ישויות, סימון יתר של אגרגציה.
4. ניתוח uncertainty: האם הסוכן יודע לסמן מקרים שלא ניתן להכריע בהם.

מדדים אפשריים:

1. micro/macro F1 מול adjudicated human labels.
2. Jaccard similarity בין קבוצות התוויות.
3. per-label precision/recall.
4. שיעור שאלות שבהן נדרש adjudication.
5. שיעור שאלות שבהן הסוכן סימן `insufficient_context`.

## שלב 6 - הרחבה מבוקרת לדאטסטים
רק אחרי פיילוט אנושי וסוכני, מרחיבים לדאטסטים נוספים.

סדר ההרחבה המומלץ:

1. דאטסטים עם גישה מלאה למסמכים והקשר.
2. דאטסטים עם ראיות אך בלי מטאדאטה עשיר.
3. דאטסטים עם פורמט בעייתי או הקשר חלקי, רק אם הם חשובים להשוואה.

בכל דאטסט צריך לשמור:

1. מדגם ידני קטן לביקורת.
2. תיעוד של מגבלות הדאטסט.
3. שיעור שאלות שלא ניתן להכריע לגביהן.
4. הערכת התפלגות מחלקות.

## שלב 7 - חישוב כיסוי
חישוב הכיסוי צריך להיות מפורק:

1. כיסוי כללי: אחוז השאלות שקיבלו לפחות מחלקת קרקוע אחת.
2. כיסוי לפי דאטסט.
3. כיסוי לפי רמת הקשר זמינה.
4. שיעור שאלות `out_of_scope`.
5. שיעור שאלות `insufficient_context`.
6. שיעור שאלות רב-מחלקתיות.
7. שיעור שאלות אונטולוגיה ואגרגציה בכל דאטסט.

נוסחה בסיסית:

```text
coverage = questions_with_at_least_one_core_label / all_answerable_questions
```

נוסחה אופרטיבית, כאשר יש שאלות שלא ניתן להכריע לגביהן בגלל מגבלת דאטסט:

```text
operational_coverage = questions_with_at_least_one_core_label / (all_answerable_questions - insufficient_context)
```

## תוצרים לקראת מימוש
בסוף שלב טענה 1 צריכים להיות:

1. `datasets/candidates.csv` - רשימת דאטסטים מועמדים וציוני התאמה.
2. `reports/dataset_discovery.md` - ניתוח הדאטסטים והחלטת ישימות.
3. `label_schema.json` - שמות תוויות והגדרות.
4. `annotation_guidelines.md` - הנחיות תיוג.
5. `data/normalized/*.jsonl` - רשומות שאלה בפורמט אחיד.
6. `annotations/manual_pilot/*.jsonl` - תיוגי פיילוט.
7. `annotations/adjudicated/*.jsonl` - תיוגים מוכרעים.
8. `annotations/agent_traces/*.jsonl` - פלט מלא של סוכן התיוג.
9. `reports/agent_vs_human.md` - השוואת סוכן למתייגים.
10. `reports/coverage_summary.md` - סיכום כיסוי.
11. `reports/boundary_cases.md` - מקרי גבול והחלטות.

## סדר ביצוע מומלץ
1. להשלים סקר דאטסטים ולמלא registry ראשוני.
2. לבצע סינון לפי קריטריוני הישימות.
3. לבחור 3 דאטסטים לפיילוט ראשון: אחד ראייתי, אחד ארגוני/תמיכתי, אחד אגרגטיבי/טבלאי.
4. לנרמל 30-50 שאלות מכל אחד.
5. לבצע תיוג ידני מבוסס תוכנית פעולה.
6. לעדכן schema והנחיות לפי מקרי הגבול.
7. להריץ סוכן תיוג על אותו מדגם.
8. להשוות תיוג סוכני לתיוג אנושי.
9. להחליט אם הסוכן מספיק טוב להרחבה מבוקרת.
10. להרחיב ל-6-8 דאטסטים.
11. לחשב כיסוי והתפלגויות.
12. להחליט אם טענה 1 ממשיכה כטענת כיסוי חזקה או מתעדכנת לטענת gap על הדאטסטים.

## החלטות פתוחות
1. האם יעד 30-40 אחוז לאונטולוגיה ואגרגציה צריך להיות תנאי קשיח או יעד מנחה?
2. כמה שאלות צריך במדגם הראשוני כדי להעריך התפלגות מחלקות בלי להטעות?
3. האם לשמור את מטאדאטה ומבנה תיקיות כתווית אחת במאמר, אך לפצל פנימית בניסוי?
4. האם אגרגציה על טבלאות פיננסיות מספיק קרובה לאגרגציה על ישויות ארגוניות, או שהיא רק proxy?
5. עד כמה לאפשר לסוכן לחפש מחוץ לשדות שהדאטסט מספק?
